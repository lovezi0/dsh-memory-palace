## 移植 WorkBuddy 记忆系统到 DeepSeek Harness（dsh-memory-palace 插件）

把 WorkBuddy 的文件式记忆（用户级 `~/.workbuddy/MEMORY.md` + 工作区 `<cwd>/.workbuddy/memory/` 下的 `MEMORY.md` 与每日日志）移植为一个独立 dsh 插件。

### 交付物（均在 `D:\Workspace\AI\workbuddy\dsh-memory-palace`）
- `src/memory.mjs`：插件主体（ESM JS）。读取用**同步 node:fs** 注入 system prompt；`turn/end` 事件**异步**写当日日志；`memory_note` 工具写工作区 `MEMORY.md`；>30 天日志蒸馏进 `MEMORY.md` 后删。
- `cordis.yml`：`--patch` 覆盖层，`name` 指向 `src/memory.mjs` 绝对路径。
- `test-load.mjs`：cordis 单元测试，验证加载 + 读写全链路（已通过）。
- `node_modules` 符号链接 → `D:\DeepSeek Harness\node_modules`（解决跨目录依赖解析）。

### 关键决策（已与用户确认）
- 真源必须保持**人类可读 Markdown**；排除 `dsh-storage`（落 JSON，与可读冲突）。
- 读用同步 node:fs（`dsh-system-prompt` 的 `section.text` 不 `await`，必须同步返回字符串）；写用异步 node:fs。
- 集成用官方 `--patch`（harness 零改动），不碰 profile 的 `package.json` / pnpm workspace。

### 环境坑（排查记录）
- **跨目录 import**：插件在 dsh-memory-palace，import `@deepseek-ai/*` 需 `node_modules` 符号链接指向 harness；否则 `Cannot find module`。
- **pnpm 路径错是 Git Bash 专属**：corepack 的 pnpm.js 在 Git Bash 下解析出 `D:\c\Program Files...` 坏路径，**PowerShell 里 pnpm 正常**。所以本机启动推荐在 PowerShell 用 `pnpm dsh web --patch <path>`（不必退而用 `node .../bin.js`）。
- **genie-safe-delete shim**：WorkBuddy 终端注入 `NODE_OPTIONS=--require=.../genie-safe-delete.cjs`，会拦 harness 启动时的 profiles 符号链接修复。若在 WorkBuddy 终端内启动，须先卸掉该变量（PowerShell: `$env:NODE_OPTIONS=""`；Git Bash: `env -u NODE_OPTIONS`）。
- **运行时静默**：web / headless / dump-config 在当前 Windows 自动化环境全部静默退出、无 stdout（正常日志被吞，仅运行时 throw 可见）。故用 cordis 单元测试（`test-load.mjs`）验证插件逻辑，无法在此环境观察 web 运行时。

## dsh 修复：cordis.patch.yml 必须是顶层数组
- 坑：移除插件 patch 注入块后若只留注释，dsh web 启动报 `must be a top-level YAML array of loader patch entries`（dsh-app-boot/lib/index.js:840 parsePatchList）。
- 正确做法：cordis.patch.yml 即使为空也必须写成 `[]`（可保留注释行），不能是纯注释。
- 校验法：用 `D:/local-repo/nodejs/node_modules/@deepseek-ai/dsh/node_modules/yaml` 的 parse 加载，断言 Array.isArray 为 true。
- 注：cordis.yml 默认即 `[]`，正常；memory-palace 从未进入 dsh.profile.bundles/dependencies（当初是手写 patch 注入，已清理）。

## 记忆写入缺陷修复（v0.4.0）——基于真实会话回放
- 用户提供 `test/session.jsonl`（347 行真实会话）暴露两个问题：
  1. **用户级记忆写不进去**：插件此前只有 `memory_note`（写项目级），没有任何工具写 `~/.deepseek-harness/MEMORY.md`；AI 尝试 run_code 拼路径时 `process.env` 为空数组（沙箱无环境变量），HOME 取不到，最后反问用户路径。
  2. **项目级重复写入**：`memory_note` 无去重，AI 在同一轮反复调用 `tools.memory_note`（同内容），MEMORY.md 里同一句出现 5 次。
  3. 诱因：`memory_note` description 含 "user preference" 字样，误导 AI 当用户级工具用。
- 修复（`src/index.mjs`）：
  - 新增公共 `appendLineDedup(file, line)`：目标文件已含该行则跳过，返回是否写入。
  - `memory_note` 改走 appendLineDedup（逐目录去重），description 明确"项目级"并指向 `memory_note_user`。
  - 新增工具 `memory_note_user`：写 `expandHome(cfg.userMemoryPath)`（默认 `~/.deepseek-harness/MEMORY.md`），自动 mkdir + 去重。
  - systemPrompt intro 提示两个工具职责边界（项目级用 memory_note / 跨项目用 memory_note_user）。
- 验证：`test-load.mjs` 新增场景 3（去重：重复调用只写 1 次，返回 "already had it"）与场景 4（`memory_note_user` 独立 Context + 临时 userMemoryPath：首次写入、重复跳过、文件 1 条）全绿；client smoke 仍 SMOKE OK。
- 版本：0.3.0 → 0.4.0。
- 注意：AI 在 run_code 里 `tools.memory_note` 直接可用（dsh 的 run_code 桥接 tools.*），但**直接**调 `memory_note` 工具会报 "unknown tool: only run_code is callable directly"（web 环境策略，非插件问题）。
